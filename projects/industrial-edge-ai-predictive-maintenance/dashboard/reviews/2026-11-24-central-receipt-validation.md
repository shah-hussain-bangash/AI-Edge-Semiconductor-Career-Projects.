# Central receipt validation — 24 November 2026

Reviewed baseline: `dc4134cc2fd1307f3262694d13f1bde0dc34af92`, draft PR #2. Scope: the existing synthetic SQLite delivery spool and central API response handling. All verification uses disposable synthetic data. Loopback worker tests use an isolated test server, not the running user dashboard.

## Demonstrated defect

The spool checked receipt tier and matching event/content hashes, but required only a truthy `receipt_id`. Reproductions supplying a Boolean, integer or object ID marked the observation `delivered`; they also omitted the commit timestamp. These responses do not conform to receipts generated by the existing central API, which uses a 32-character lowercase hexadecimal identifier and an aware commit timestamp.

## Change and compatibility

Before saving a delivered outcome, the spool now requires the existing central receipt identifier format and a bounded, parseable timezone-aware commit timestamp, in addition to the existing tier/event/content checks. A malformed success response follows the existing `invalid-central-receipt` blocked path. The original queued payload is retained, its receipt stays null and the record remains available for investigation. There is no automatic deletion or retry of a blocked record.

Actual central API responses retain their format. Three synthetic receipt fixture helpers were corrected to use that format. Existing saved delivery history is not rewritten or retroactively verified. This change does not authenticate a receipt, verify the remote clock, prove an arbitrary server committed data or establish physical acquisition. A correctly shaped response remains a claim from the configured endpoint.

## Verification

New regressions reject 18 malformed identifier/timestamp combinations, including wrong types, invalid lengths/characters, missing/null timestamps and timezone-free timestamps. They assert blocked state, one retained queue record, unchanged payload, null receipt and the sanitized error label. A positive regression checks preservation of the exact valid receipt.

All 46 tests passed across `test_delivery.py`, `test_delivery_history.py`, `test_delivery_capacity.py`, `test_delivery_timing.py`, `test_acquisition_registry.py` and `test_observation_queries.py`. These also exercise abrupt process exit and lease reclamation, expired-worker fencing, response loss after an actual test API commit, duplicate suppression, conflicts, capacity, saved timing/history, access and observation inspection. Existing test-client deprecation warnings did not block execution. No additional hardware, dashboard features, merge or deployment is included. The original 30-product selection is unchanged; physical acceptance and equipment authorization remain pending/false.
